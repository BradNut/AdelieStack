# API Localisation (Paraglide)

Human-readable API text (error messages, mail copy, validation messages) comes from a Paraglide 2.x message catalogue, not string literals.

## Catalogue

- Project: `apps/api/project.inlang/settings.json`. Messages: `apps/api/messages/{locale}/api.json`.
- The API owns its catalogue (like SCP) so web never ships API strings and the API build never reads `apps/web`.
- Locale list, base locale, and the `./messages/{locale}/<namespace>.json` layout must match `apps/web/project.inlang`. `common/i18n/tests/catalogue.test.ts` fails if they drift or if any locale is missing a base-locale key.
- Add a locale in both apps' `settings.json` plus a `messages/<locale>/` dir in each.

## Compile

- `pnpm --filter @adelie/api paraglide:compile` writes `src/lib/paraglide/` (gitignored, with `.d.ts` so `tsc` never typechecks the DOM-aware runtime).
- `dev`, `build`, `check`, and `test:unit` compile first. `paraglide:watch` recompiles on edit; `tsx watch` then restarts.
- Turbo runs `@adelie/api#paraglide:compile` before `@adelie/web#check`, since web typechecks API source through the RPC contract.

## Request Locale

1. `requestLocale` middleware (`common/middleware/locale.middleware.ts`, after `contextStorage()`) reads `Accept-Language`, honouring q-values; region tags map to their base language (`de-AT` -> `de`).
2. Missing, empty, or unsupported headers fall back to the base locale `en`.
3. The result is stored in `c.var.locale` and echoed as `Content-Language` (`Vary: Accept-Language`).
4. `common/i18n` points Paraglide's `getLocale()` at the current Hono context, so `m.*()` anywhere in a request is localised. Outside a request (jobs, scripts) it returns `en`; pass `{ locale }` explicitly there (e.g. a user preference for mail).

## Usage

- Import `m` from `common/i18n` with relative paths (files are reachable from the RPC contract; no `$lib`).
- A key missing in a non-base locale falls back to the base-locale text at compile time; a key missing from the base locale is a type error.
