# API Localisation (Paraglide)

Human-readable API text (error messages, mail copy, validation messages) comes from a Paraglide 2.x message catalogue, not string literals.

## Catalogue

- Project: `apps/api/project.inlang/settings.json`. Messages: `apps/api/messages/{locale}/api.json`.
- The API owns its catalogue (like SCP) so web never ships API strings and the API build never reads `apps/web`.
- Locale list, base locale, and the `./messages/{locale}/<namespace>.json` layout must match `apps/web/project.inlang`. `common/i18n/tests/catalogue.test.ts` fails if they drift or if any locale is missing a base-locale key.
- Add a locale in both apps' `settings.json` plus a `messages/<locale>/` dir in each.

## Compile

- `pnpm --filter @adelie/api paraglide:compile` writes `src/lib/paraglide/` (gitignored, with `.d.ts` so `tsc` never typechecks the DOM-aware runtime).
- `dev`, `build`, and `check` compile first. Vitest compiles in a global setup (`src/test/paraglide.global-setup.ts`), so `pnpm test` and a direct `pnpm vitest run <file>` both work in a fresh checkout. `paraglide:watch` recompiles on edit; `tsx watch` then restarts.
- Turbo runs `@adelie/api#paraglide:compile` before `@adelie/web#check`, since web typechecks API source through the RPC contract.

## Request Locale

Web and API resolve the Request Locale in one order, `REQUEST_LOCALE_ORDER` in `@adelie/shared/constants` (Paraglide strategy names): the locale cookie, then `Accept-Language`, then the base locale `en`. An explicit choice (the cookie) beats the browser's language. Web passes it to the Paraglide Vite plugin; the API middleware resolves with it. Keep both apps' `paraglide:compile --strategy` flags equal to it, because Paraglide tree-shakes the strategies a compile does not name (web's `i18n-strategy.test.ts` and the API locale middleware tests fail on drift). Never add `url`: the web hook passes the original request through.

1. `requestLocale` middleware (`common/middleware/locale.middleware.ts`, after `contextStorage()`) reads the Paraglide locale cookie (`PARAGLIDE_LOCALE`, forwarded by the web proxy). An unsupported value is skipped.
2. Otherwise it reads `Accept-Language`, honouring q-values; region tags map to their base language (`de-AT` -> `de`).
3. When neither names a supported locale, it falls back to the base locale `en`.
4. The result is stored in `c.var.locale` and echoed as `Content-Language` (`Vary: Accept-Language, Cookie`).
5. `common/i18n` points Paraglide's `getLocale()` at the current Hono context, so `m.*()` anywhere in a request is localised. Outside a request (jobs, scripts) it returns `en`; pass `{ locale }` explicitly there (e.g. a user preference for mail).

## Usage

- Import `m` from `common/i18n` with relative paths (files are reachable from the RPC contract; no `$lib`).
- Mail takes an explicit locale: each template receives one and calls `m.key(params, { locale })`, never the ambient locale. It is currently the request's locale, chosen where the email is sent (`auth/auth.mail.ts` and the two-factor OTP send in `auth/auth.config.ts`).
- A key missing in a non-base locale falls back to the base-locale text at compile time; a key missing from the base locale is a type error.
