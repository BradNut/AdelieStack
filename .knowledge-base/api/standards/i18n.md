# API Localisation (Paraglide)

Human-readable API text (error messages, mail copy, validation messages) comes from a Paraglide 2.x message catalogue, not string literals.

## Catalogue

- Project: `apps/api/project.inlang/settings.json`. Messages: `apps/api/messages/{locale}/api.json`.
- The API owns its catalogue (like SCP) so web never ships API strings and the API build never reads `apps/web`.
- Locale list, base locale, and the `./messages/{locale}/<namespace>.json` layout must match `apps/web/project.inlang`. `common/i18n/tests/catalogue.test.ts` fails if they drift or if any locale is missing a base-locale key.
- Add a locale in both apps' `settings.json` plus a `messages/<locale>/` dir in each.

## Compile

- `pnpm --filter @adelie/api paraglide:compile` writes `src/lib/paraglide/` (gitignored, with `.d.ts` so `tsc` never typechecks the DOM-aware runtime).
- `dev`, `build`, and `check` compile first. Vitest compiles in a global setup (`src/test/paraglide.global-setup.ts`), so `pnpm test` and a direct `pnpm vitest run <file>` both work in a fresh checkout. `paraglide:watch` recompiles on edit; `tsx watch` then restarts.
- Turbo runs `@adelie/api#paraglide:compile` before `@adelie/web#check`, since web typechecks API source through the RPC contract.

## Request Locale

1. `requestLocale` middleware (`common/middleware/locale.middleware.ts`, after `contextStorage()`) reads `Accept-Language`, honouring q-values; region tags map to their base language (`de-AT` -> `de`).
2. Missing, empty, or unsupported headers fall back to the base locale `en`.
3. The result is stored in `c.var.locale` and echoed as `Content-Language` (`Vary: Accept-Language`).
4. `common/i18n` points Paraglide's `getLocale()` at the current Hono context, so `m.*()` anywhere in a request is localised. Outside a request (jobs, scripts) it returns `en`; pass `{ locale }` explicitly there.

## Usage

- Import `m` from `common/i18n` with relative paths (files are reachable from the RPC contract; no `$lib`).
- Mail takes an explicit locale: each template receives one and calls `m.key(params, { locale })`, never the ambient locale. Where the email is sent (`auth/auth.mail.ts` and the two-factor OTP send in `auth/auth.config.ts`), the locale is chosen by `mailLocale(user)` (see [Mail Locale](#mail-locale)), never by the Request Locale directly.
- A key missing in a non-base locale falls back to the base-locale text at compile time; a key missing from the base locale is a type error.

## Mail Locale

Every email to an account is written in `Preferred Language ?? Request Locale ?? en`: the `users.locale` field (`auth/auth.preferred-language.ts`) when it holds a supported locale, otherwise the request's locale, which itself falls back to `en`. Both Link Emails, every Security Event (including the email-change notice to the old address) and the two-factor OTP go through `mailLocale`; a new sender must too, and the user it receives must carry `locale` (load it if a callback only gives an id or email).

Why the preference beats the request: the request is not always the account holder's. An attacker changing an account would otherwise get the owner's Security Event warning written in the attacker's browser language, and the email-change notice to the old address follows whichever browser opened the link in the new mailbox. Do not "fix" a Security Event back to the Request Locale.

- **Writes**: only a supported locale or `null` can be stored (a Better Auth field validator); anything else is a `400 VALIDATION_ERROR`. The account holder saves it through update-user, which needs no fresh session and sends no Security Event email: it is a setting, not a credential.
- **Seeding**: self and social sign-up save their Request Locale; admin-created and seeded accounts keep `null`, since that request carries the creator's language. Existing accounts are not backfilled.
- **Stale values**: a stored locale the catalogue no longer lists counts as no preference and the row is left as it is, so removing a locale needs no data migration.
